Room Parent Web Portal — 3 Directions

New surface Tony described: a lightweight web portal room parents log into (phone number + code) to run the master calendar, lunch menu, event push, AI email compose, and — per Ahmad's follow-up — donation/fundraising tracking, replacing the current spreadsheet. Since this shell will carry all of those sections, three structurally different takes below before committing to one. Fundraising is fleshed out in full on every direction since that's the concrete spec; the other four sections are shown as nav stubs so you can judge the overall shape. All three are live — the donation/expense forms actually add rows, totals recalc, receipt upload shows a real thumbnail, and Export downloads a real CSV of what's in the table.

Direction A · Sidebar Admin

Full SaaS dashboard — persistent nav, data tables

Left sidebar with all 5 sections always visible, dense tables for the donation/expense logs. Reads like a proper back-office tool — most scalable if a class ends up with 40+ logged transactions, easiest to scan at a glance.

Trade-off: heaviest of the three, most "enterprise SaaS" — least like the rest of Sprout's warm, parent-facing voice. Best if room parents will mostly use this on a laptop.

Direction B · Mobile-First Simple

Phone-web portal, one thumb, one column

Since room parents log in with a phone number + code, this direction assumes they'll mostly check it on their phone in a browser tab — big hero stat, stacked cards instead of tables, huge tap targets.

Trade-off: friendliest and fastest to use on the go, but a class with a long transaction history gets a long scroll instead of a scannable table. Best if this is mostly a quick "log it and move on" tool.

Direction C · Warm Card Dashboard

Desktop-width but Sprout-warm, not SaaS-gray

Light pill tabs instead of a sidebar, everything in soft cream cards matching the app's own visual language (the same avatar/badge treatment as the Member Directory). New entries expand inline in place rather than a separate form panel.

Trade-off: the middle ground — more breathing room and scan-ability than B, warmer and more "Sprout" than A. Slightly less information-dense than A's tables if the log gets very long.
